# Working on thisguyskills

This repository is Martin's research and explanation toolkit. It gathers evidence, explains projects, investigates cloud behavior, creates visual plans, and captures or recalls knowledge in Martin's Brain when requested. Implementation, deployment, public publishing, and global installation are separate tasks. Pstack runs only when explicitly requested.

- Keep a small set of independent skills: excalidraw, project-research, gather-context, plan-artifact, session-history, cloud-investigate, notion-brain, and yaak-query. Add a skill only when a new responsibility earns its own entrypoint. Load supporting files only when needed. Keep general documentation in docs/; preserve Excalidraw's existing installation reference.
- Keep the layout flat: one folder per skill at the repository root, and flat inside it too: `SKILL.md`, `LICENSE.txt`, and supporting `.md` files side by side. Only `agents/` (host metadata such as Codex's `agents/openai.yaml`) and `scripts/` are allowed as subfolders. Long-form docs, workflows, examples, provenance, and plans go in `docs/`; tooling and CI go in `.github/`. Any other root folder fails validation.
- Every skill gets a `README.md` section headed by its name linked to its folder with a short description and quoted trigger phrases, plus a row in the install table. Add both when you add a skill.
- Preserve independent use: each skill includes inputs, outputs, and stopping conditions. Sibling skills are optional helpers except when the full workflow requires their quality gate.
- Research upstream changes at exact revisions. Update provenance and license notices with adaptations. Never vendor Pstack or overwrite skill folders from upstream tooling.
- Run `node .github/scripts/validate-skills.ts` and `node --test .github/scripts/tooling.test.ts` (or `npm run check` and `npm test`). Walk through `docs/examples/scenarios.md` when behavior changes; structural validation does not prove agent behavior.
- Use synthetic data in fixtures. Never send real customer data to third-party AI services; prefer the local codebase, git history, and user-provided files before external sources. Do not modify live Linear issues to test these skills.
- Communicate directly in casual first person; keep updates short and terminal-first; use `->` notation for flows; include sources and confidence levels for factual guidance.
- Keep runtime-specific setup in `docs/compatibility.md`. Installing global skills, publishing this repository, and creating live issues are separate tasks.
- Commit only as Martin Patino <mpatino117@gmail.com>. Use a conventional subject under 72 characters and a detailed body explaining what, why, and non-obvious approach. Use bullets for multiple meaningful changes and reference tickets when available. Never add AI attribution, co-author trailers, or AI sign-offs.
