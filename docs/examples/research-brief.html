Make event delivery understandable

How can people tell whether an event is waiting, retrying, or finished?

Keep the existing queue and worker. Add an explicit delivery lifecycle and a small status view so people can distinguish a delayed event from a failed one. Agree on retry ownership before building the view.

Updated 2026-10-06Evidence -> explanation -> plan

Synthetic research example only. No customer payloads, real incidents, cloud accounts, or live source systems were queried. Current means current within this fixture; the proposed behavior has not been implemented or tested.

01 / Research

The domain before the infrastructure

An event describes something that happened. A delivery is the attempt to notify a destination about that event. One event can have several deliveries, and one delivery can have several attempts.

Think of the event as a letter and the delivery as the tracked shipment. Retrying the shipment should not create a new letter. Event identity must survive retries so the destination can recognize duplicates.

S1
Read the supporting detail

Entities: Event, Delivery and Attempt. The producer owns event creation; the worker owns an attempt; the destination owns acceptance. The delivery lifecycle is waiting -> attempting -> succeeded, with retrying or failed outcomes when an attempt cannot complete.

The queue provides transport. It does not own the business definition of success. A message disappearing from a queue is not enough evidence that the destination accepted it.

02 / Research

What happens today

The producer sends an event to the queue. A worker reads it and calls the destination. In this fixture, people can see that a delivery is pending, but cannot tell whether a callback is running or waiting for a retry.

Synthetic example: event evt_demo_001 asks a destination to refresh a demonstration record. The destination times out. The record stays pending, so a person has to inspect logs to learn what happened.

S1 S2
Read the supporting detail

The fixture establishes the visible pending state and the timeout path. It does not establish deployed retry intervals, actual traffic volume, or production failure rates.

A log query without the event correlation ID can miss the relevant attempt. Empty log results should be reported as incomplete evidence, not as proof the worker never ran.

03 / Research

The smallest useful change

Record each delivery attempt and expose its state. The view should answer: what happened, when did the last attempt run, and is another attempt expected? Keep payloads out of the status view.

The queue and worker remain the transport path. Persisted delivery state becomes the explanation path. A timeout can be shown as retrying only when retry policy actually schedules another attempt; otherwise it is failed.

S3
Read the supporting detail

This is a proposal with medium confidence (~70%). It fits the synthetic evidence, but ownership, retention, expected volume and destination idempotency still need a decision.

No cloud vendor or new service is selected. Reuse the project's existing storage when it can represent this lifecycle cheaply. Add infrastructure only when workload evidence requires it.

04 / Research

Failure paths and ownership

A duplicate event must keep the same identity. A late response must not turn a succeeded delivery back into a failed one. Permission checks must prevent one organization from seeing another organization's delivery history.

After migration, old pending records may lack attempt evidence. Label them as legacy or unknown until verified. Do not infer success from their age or from an empty queue.

S1 S3
Read the supporting detail

Observe producer -> queue -> worker -> destination using correlation IDs and timestamps. Mark where observation ends. The status record should contain metadata needed for explanation, not raw customer request/response bodies.

A rollback can disable the new view while preserving collected attempt metadata. Decide retention and reconciliation rules before migrating existing records.

Plan and completion checks

  1. Settle lifecycle ownership

    Outcome
    The team agrees what each state means and who can change it
    Depends on
    Producer and worker ownership; retry policy
    Complete when
    A timeout, duplicate and late success each have an agreed state transition

  2. Capture attempt metadata

    Outcome
    An event can be traced without exposing payloads
    Depends on
    Lifecycle decision and existing storage constraints
    Complete when
    Synthetic success/failure/retry attempts retain one event ID and distinct attempt IDs

  3. Build the authorized status view

    Outcome
    A person sees the last outcome and next expected action
    Depends on
    Persisted lifecycle and tenant permissions
    Complete when
    A synthetic failure is understandable; a different tenant cannot read it

  4. Roll out and reconcile legacy records

    Outcome
    New records are explained and old unknowns remain visible
    Depends on
    Migration, retention and rollback decisions
    Complete when
    Legacy records stay explicitly unknown; disabling the view preserves recorded evidence

Open questions

  • Who owns the retry schedule and the terminal failure decision?
  • How long should metadata be kept, and what workload is expected?
  • Does the destination already enforce event idempotency?
